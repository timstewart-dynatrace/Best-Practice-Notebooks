Series: ONBRD — Dynatrace Onboarding | Notebook: 3 of 10 | Created: December 2025 | Last Updated: 11/16/2026

Your Network Gateway to Dynatrace

ActiveGate is a lightweight component that routes traffic between your infrastructure and Dynatrace. This notebook covers when you need ActiveGate, how many to deploy, where to place them, and installation steps - including comprehensive Kubernetes deployment options.

1. What is ActiveGate?

ActiveGate is a proxy and routing component that connects your environment to Dynatrace.

Component Purpose
Environment ActiveGate Routes OneAgent traffic and runs extensions; private synthetic monitors run on a separate Synthetic-enabled ActiveGate
Cluster ActiveGate Dynatrace Managed only — the cluster's mediating proxy for OneAgent and digital experience traffic from outside its network

Note: This notebook covers Environment ActiveGate for Dynatrace SaaS. On Managed, "use one or more Cluster ActiveGates as mediating proxies for pre-processing of OneAgent and DEM traffic"; both ActiveGate types on Managed are covered in DTM-04: ActiveGate Deployment on Managed. (Managed deployments (DT docs))

ActiveGate Capabilities

Capability Description
Traffic Routing Proxies OneAgent data to Dynatrace
Extensions 2.0 Runs Python-based extensions locally
Synthetic Monitoring Private synthetic locations — on a dedicated Synthetic-enabled ActiveGate only (see the note below)
Cloud Integrations Classic AWS / Azure metric polling (or use the Clouds app for direct connections); the GCP integration needs no ActiveGate on SaaS
Kubernetes API Cluster monitoring via API
Log Ingest Generic log ingest endpoint

Synthetic ActiveGates do nothing else. "A clean ActiveGate installation for the purpose of synthetic monitoring disables all other ActiveGate features, including communication with OneAgents." Plan private synthetic locations on their own ActiveGates, installed from the Install ActiveGate wizard in Discovery & Coverage with Purpose → Synthetic, and never count them toward routing capacity. (Install a Synthetic-enabled ActiveGate (DT docs))

OneAgent Attribute Enrichment (OneAgent 1.333+): OneAgent can enrich all telemetry (metrics, spans, logs, events) with primary fields (dt.security_context, dt.cost.costcenter) and primary tags (primary_tags.environment, primary_tags.team) at the source. More efficient than auto-tags — feeds directly into OpenPipeline routing, bucket assignment, and Grail permissions. Configure via the installer's --set-host-tag at install time, or oneagentctl --set-host-tag … --restart-service afterwards (set parameters apply only after a OneAgent restart). See docs.

Routing OneAgent Traffic: Through an ActiveGate or Direct?

When every host can already reach your SaaS environment, routing OneAgent traffic through an ActiveGate is a design choice, not a requirement. "In the absence of an ActiveGate, data collected by OneAgent is sent directly to the Dynatrace Cluster", and the OneAgent install guide puts it the same way: you "may choose to either provide direct access to the Dynatrace cluster or set up an ActiveGate." Each side has costs:

Factor Route through an ActiveGate Go direct to your SaaS environment
Egress and allowlisting Only the ActiveGates need outbound 443. For hosts without internet access, Dynatrace says to "install an ActiveGate to serve as a single access point, rather than opening the firewall for multiple hosts running OneAgents", so the firewall and proxy rules name a few ActiveGates. Every monitored host needs outbound HTTPS 443 to your environment, through your firewall or proxy.
Proxy configuration Configured on the ActiveGates: "You can use a single proxy for all outgoing traffic", set in the ActiveGate configuration. Dynatrace says the single-access-point approach "greatly reduces the effort of managing and maintaining firewall and/or proxy configuration settings." Each OneAgent host that reaches the environment through a proxy needs that proxy set on the host, with oneagentctl --set-proxy or at install time.
Network overhead The routing module "collects messages from OneAgent instances and builds bulks, which are then sent in compressed form". Dynatrace says this "can reduce network overhead considerably, depending on the number of OneAgent instances" behind the ActiveGate. No ActiveGate-side bulking: each OneAgent connects to the environment on its own.
Connections at the egress OneAgent connections end at the ActiveGates, and only the ActiveGates hold connections out through your NAT or firewall. Dynatrace says the ActiveGate lets you "reduce your interaction with Dynatrace to one single point—available locally", and that it "reduces the complexity of network connections." Every OneAgent on every host holds its own connections through the shared egress device. The docs publish no per-host connection count. In field experience it grows with the number of instrumented processes on the host (see the note below).
Infrastructure to run ActiveGate hosts to size (§ 3 and FAQ-10), keep updated (FAQ-05) and run at two or more per network zone for high availability. Auto-update covers host-based ActiveGates only: "Auto-update and One-click update functionalities are limited to host-based—using installer—deployment only." Nothing to deploy, size, patch or update.
Capacity The ActiveGates in a zone carry every host behind them, so their capacity, and the survivor's capacity when one is down (§ 3), caps the zone. No intermediate tier to saturate.
Operating-system lifecycle Every ActiveGate host must stay on a supported OS. The § 3 table lists nine OS versions that lose ActiveGate support between 11/01/2026 and 01/01/2027. No additional OS to track.
Locality and failover Network zones keep OneAgents on nearby ActiveGates, and "You can still use ActiveGates in other zones as a backup option in case primary ActiveGates becomes unavailable". See the fallback table below. No zone design. Resilience is the host's own path to your environment.
Installer cache The requirements page budgets 4 GB for "ActiveGate and OneAgent cached installers and container images—if such will need to be stored." Hosts download installers from the environment.
Reuse A routing/monitoring ActiveGate you already run for remote extensions, Kubernetes monitoring or classic cloud polling can also route OneAgent traffic. A Synthetic-enabled ActiveGate cannot: a clean Synthetic installation "disables all other ActiveGate features, including communication with OneAgents" (§ 1). No reuse needed.
Memory dumps OneAgent uploads Java, .NET and Node.js memory dumps to the ActiveGate, which stores them for download. Dynatrace "doesn't allow you to upload dumps to the Dynatrace cluster in the cloud." No central store. Dumps stay on the monitored host only for a limited time: "when OneAgent periodically empties the directory, the file size could be 0 bytes." Copy a dump off the host before it ages out.
z/OS The zRemote module "routes that data, compressed and encrypted, via its local ActiveGate to Dynatrace." Not possible: z/OS monitoring always goes through an ActiveGate.

Recommended approach: route through ActiveGates when hosts cannot or should not have direct egress, when your security team wants monitoring traffic to leave through a few known hosts, or when a large fleet shares one NAT or firewall egress (see the note below). Go direct when hosts already have outbound access, the fleet behind each egress is small, and nothing else requires an ActiveGate (central memory dump storage and z/OS monitoring both do). Choose per network zone: a sealed data center can route through ActiveGates while cloud workloads with egress go direct.

Large fleets going direct can exhaust the egress device. In field experience, each instrumented process on a full-stack host talks to your environment on its own. A host with log monitoring and 20 injected processes then holds on the order of 25 TCP connections. Dynatrace does not publish that figure, so measure it on one of your own hosts before planning around it: on Linux, ss -tn state established '( dport = :443 )', then count the lines whose peer is your environment's address.

Across a fleet, all of those connections pass through the NAT or firewall the hosts share for internet egress. A device that translates everything to one public IP, from a single port pool shared across destinations, has at most 65,535 source ports, and fewer once reserved ranges are excluded. 2,000 hosts × 25 connections uses about 50,000 of them and leaves roughly 15,000 for everything else on the network. At 30 instrumented processes per host the pool is gone: some OneAgent connections fail, and so does other outbound traffic. Devices with a pool of public IPs, or that allocate ports per destination, have more port headroom, but their session table still has to hold every connection.

One large enterprise deployment that sent its whole fleet direct saw sites lose internet connectivity this way until it deployed ActiveGates. Before going direct at scale, ask your network team for two numbers: the egress device's NAT port capacity and its session-table limit.

Kubernetes clusters usually run an ActiveGate anyway. Kubernetes/OpenShift monitoring is an ActiveGate module, and the Operator's full-stack example deploys an ActiveGate with the routing and kubernetes-monitoring capabilities. In-cluster OneAgents can still go direct, so for a cluster the question is usually whether to route through the ActiveGate you already run there (§ 7), not whether to deploy one.

Going direct does not stay direct by itself. The connectivity scheme says "OneAgent will connect to an Environment ActiveGate, if one is present", and OneAgents with no network zone "try to connect to any ActiveGate in a random order". If you later deploy an Environment ActiveGate for extensions or Kubernetes, hosts that can reach it may start routing through it. Use network zones to decide which hosts use which ActiveGates.

When every ActiveGate in a zone is down

Each network zone has a fallback mode (Deployment Status → Network zones → Edit → Fallback mode). It decides what OneAgents do when "no ActiveGates are available in this network zone and there are no alternative network zones":

Fallback mode Behavior when no ActiveGate in the zone or its alternative zones is available
Any ActiveGate (default) "traffic is routed to any available ActiveGate, including an ActiveGate in the default zone."
Only default zone "traffic is routed only to an available ActiveGate in the default zone. ActiveGates in other zones aren't considered."
None "Traffic stays within the primary zone and its alternative zones. If no ActiveGate in those zones is available, OneAgents don't send data to another zone."

On SaaS, the connectivity scheme says OneAgent connects to the SaaS cluster "directly, if no connection to an Environment ActiveGate is possible." Fallback only helps if the host can reach the fallback target. A host in a sealed network that loses every ActiveGate it can reach has nowhere to send data, so plan two or more ActiveGates per zone (§ 3) and configure alternative zones the hosts can reach.

3. How Many ActiveGates?

Sizing Guidelines

FAQ-10 owns the ActiveGate sizing decision. FAQ-10: How do I size and scale ActiveGates? carries the current published per-shape capacity tables, the 50% CPU / 80% memory headroom rule, the survivor-capacity HA math for a multi-node zone, and the dt.sfm.active_gate.* saturation signals to watch once the fleet is running. Treat the table below as an order-of-magnitude sanity check while you plan the deployment — size the actual machines against FAQ-10 and the official requirements page.

Dynatrace publishes estimated host counts per reference instance shape for an ActiveGate that only routes OneAgent traffic. The counts assume a specific workload: "On each host, OneAgent is performing eight monitoring tasks" — infrastructure monitoring, log monitoring, full-stack monitoring of 3 Apache Tomcat and 2 Apache HTTP Server instances, and extension monitoring. The page adds that "The real number of hosts may be different depending on the monitored technologies in your environment." In steady state the ActiveGate machine "should not exceed 50% CPU and 80% memory".

c6i.large x86-64 2 3.75 GiB ~800

The reference points are AWS instance shapes (plus two s390 machine sizes). For on-premises VMs, map by vCPU and RAM rather than looking for the instance name. Compare your own hosts with the eight-task profile before reusing a count: a host with more instrumented processes than that profile fills an ActiveGate sooner.

Check the architecture before you pick an instance family. ARM64 routes more hosts per vCPU than x86-64 at the same shape, but "ActiveGate installed on the x86-64 architecture supports all functionalities. Other architectures provide only partial support." Confirm that every ActiveGate purpose you need (extensions, cloud polling, Kubernetes monitoring) works on ARM64 or s390 before you standardize on it. Windows ActiveGates are x86-64 only: "ActiveGate supports only operating systems running on the x86-64 architecture (64-bit Intel/AMD)."

Already ended (11/01/2026): Red Hat Enterprise Linux 9.4 and Ubuntu 16.04 — no longer supported for ActiveGate since that date.

Existing ActiveGates on these versions keep working right up to the date — nothing stops the moment the announcement lands. What ends is Dynatrace's commitment to fix issues and ship new ActiveGate versions for that OS. Two practical consequences for an onboarding plan:

  • Do not provision new ActiveGates on any version in this table. Amazon Linux 2 and RHEL 9.4 were the obvious defaults a year ago; RHEL 9.4 is already out of support and Amazon Linux 2 is next — pick Amazon Linux 2023, RHEL 9.8/10.2, Oracle Linux 9.8/10.2, or Rocky Linux 9.8/10.2 instead. Oracle Linux and Rocky Linux 9.8 and 10.2 are themselves already announced for de-support from 06/01/2027 (ActiveGate 1.349 release notes: "The following operating systems will no longer be supported starting 01 June 2027"), so on those distributions plan the move to the next listed minor version. On Windows, "The following operating systems will no longer be supported starting 01 August 2027 Windows: Windows Server 2016" — start new Windows ActiveGates on 2019 or later.
  • Fold the OS upgrade into the next ActiveGate update window rather than scheduling it as separate work. The update mechanics, auto-update behavior, and how to schedule those windows are covered in FAQ-05: Managing ActiveGate updates on Dynatrace SaaS.

High Availability

The sizing tables assume that "ActiveGates may be inoperable during updates, restarts or short communication problems", and that "operating ActiveGates should be able to takeover traffic of the unavailable ActiveGates". So a production zone needs at least 2 ActiveGates, and each one must be able to carry the whole zone while the other is down:

Deployment ActiveGates Basis
Minimum HA 2 per zone The takeover rule above
Load distribution 2–3 per zone Community practice
Large scale N+1 per zone Community practice: size N to carry the zone, then add one

How OneAgents spread across them. "OneAgents are load-balanced to use an ActiveGate with the lowest possible index. That is, if several ActiveGates with the low index are available, OneAgents will try to switch between the available ActiveGates on a regular basis." That is periodic switching, not per-request distribution. In community practice the load on each node is uneven over short windows, so watch per-node CPU and memory (FAQ-10) rather than assuming an even split.

Sources: Linux ActiveGate hardware and system requirements (DT docs) — "In order to ensure high availability, operating ActiveGates should be able to takeover traffic of the unavailable ActiveGates", OneAgent connectivity in network zones (DT docs) — "OneAgents are load-balanced to use an ActiveGate with the lowest possible index."

5. Generating Tokens

Downloading the ActiveGate installer needs one of two token types, depending on your environment. on a latest environment, "Platform tokens only. Classic access tokens don't exist, and v2/apiTokens isn't available."; environments migrating to Latest Dynatrace have both, and SaaS 1.343 says "We recommend platform tokens over classic API tokens for new integrations."

Environment Token Required scope Request header

7. Kubernetes Deployment (Detailed)

Deploying ActiveGate in Kubernetes requires careful consideration of where, how, and when to use containerized ActiveGates vs. traditional VM deployments.

When to Deploy ActiveGate in Kubernetes

Scenario Deploy in K8s? Reasoning
Cluster-only monitoring ✅ Yes Co-located with workloads, simplifies networking
Routing for in-cluster OneAgents ✅ Yes Lower latency, no external hops
Remote extensions ❌ Host-based ActiveGate The container image does not include the Extensions module. SQL extensions are the exception: they run on Kubernetes through the Operator, not on an ActiveGate (see the note below)
Multi-cluster routing ⚠️ Consider May need external AG for cross-cluster
Private synthetic monitoring ✅ Supported Containerized private locations are documented and auto-scale (SYNTH-04); in community practice some teams still choose VMs for a fixed egress IP
Routing for external hosts ❌ VM preferred External hosts need stable, routable IP
Air-gapped environments ❌ VM preferred Often need dedicated proxy tier

When NOT to Deploy in Kubernetes

Scenario Why VM is Better
Routing for VMs/bare metal VMs need stable IPs, not pod IPs
Private synthetic locations, when you need a fixed egress IP In community practice a VM is simpler to allow-list; both deployments are supported
Extensions polling external systems The Extensions module runs on host-based ActiveGates only
Compliance requiring dedicated hosts Some compliance requires dedicated hardware

What the container image leaves out. "The container image covers only a subset of that, provided by the core ActiveGate process." The capability matrix marks Extensions, syslog ingestion, zRemote, memory dumps and classic AWS monitoring as unavailable on a containerized ActiveGate. "Remote configuration management works for OneAgents in Full-Stack and Infrastructure Monitoring mode and for host-based ActiveGates", not containerized ones, according to a page labelled Dynatrace Classic. For SQL databases, Dynatrace documents a separate path: "Run SQL monitoring extensions on Kubernetes using Dynatrace Operator." (Dynatrace 1.346+). For the whole decision, including VM and Kubernetes trade-offs, see FAQ-28: When and where should I deploy ActiveGates?

Deployment Architecture

Kubernetes ActiveGate Sizing

Dynatrace recommends "two sets of ActiveGates for production deployments": one for Kubernetes platform monitoring (including Prometheus and KSPM), one for OneAgent traffic routing and telemetry ingest. Both are sized by cluster size — pods first, nodes second:

Cluster size Pods Nodes
Small <1,000 Up to 25
Medium 1,000–5,000 Up to 100
Large 5,000–20,000 Up to 500

Kubernetes platform monitoring ActiveGate

Cluster size CPU request CPU limit Memory request Memory limit
Small 200m 1000m 6 GiB 6 GiB
Medium 1000m 2000m 10 GiB 10 GiB
Large 2000m 4000m 12 GiB 12 GiB

OneAgent traffic routing ActiveGate

Cluster size CPU request CPU limit Memory request Memory limit Replicas
Small 250m 1000m 2 GiB 2 GiB 3
Medium 500m 2000m 4 GiB 4 GiB 3
Large 1000m 4000m 6 GiB 6 GiB 6

Platform monitoring needs far more memory than routing — budget for it before you put both jobs on one ActiveGate. The guide's advice on limits: "Use CPU limits only if required by policy." OTLP log ingest through the ActiveGate adds replicas. The guide gives a throughput per replica (about 350, 650 and 1,200 MB/min for the small, medium and large configurations) and the formula "additional replicas = ceil(expected log traffic (MB/min) ÷ throughput per replica)".

Method 1: Dynatrace Operator (Recommended)

The Dynatrace Operator manages ActiveGate lifecycle automatically.

Important: Use apiVersion: dynatrace.com/v1beta6 for new DynaKubes (v1beta5 is still served by Operator 1.11.0 but marked deprecated in its CRD from Operator 1.10.0). Operator 1.9.0 removed v1beta3 from the CRD ("Applying DynaKube resources using this version will fail") and deprecated v1beta4; Operator 1.10.0 (July 15, 2026) stopped serving v1beta4 (its CRD sets served: false, while its notes repeat "The v1beta4 version is now deprecated"); and Operator 1.11.0 (released 10/01/2026) removes it from the CRD — "Applying DynaKube resources that still use v1beta4 will fail." Check kubectl get dynakube -A -o jsonpath='{.items[*].apiVersion}' before upgrading the Operator, and move any v1beta4 DynaKube to v1beta6 first. The example below uses v1beta6 (validated against the Operator 1.11.0 CRD). v1beta6 adds OTLP exporter configuration.

Sources: Operator 1.9.0 release notes (DT docs) — "Additionally, v1beta4 is now deprecated.", Operator 1.10.0 release notes (DT docs), Operator 1.11.0 release notes (DT docs) — "The v1beta4 version has been removed from the DynaKube CRD." served / deprecated per version read from the DynaKube CRD in each release's kubernetes.yaml (Operator releases (Dynatrace GitHub)), 10/02/2026.

The example follows the sizing guide's two-set layout for Operator versions earlier than 1.11.0 (the version pinned below): one DynaKube for platform monitoring, one for routing, both sized for a small cluster.

# dynakube-activegates.yaml - two ActiveGate sets via the Operator (small cluster)
apiVersion: dynatrace.com/v1beta6
kind: DynaKube
metadata:
  name: k8s-monitoring
  namespace: dynatrace
spec:
  apiUrl: https://{tenant-id}.live.dynatrace.com/api
  tokens: dynakube              # secret created below
  networkZone: kubernetes       # network zone for the ActiveGate (and OneAgent) pods

  activeGate:
    capabilities:
      - kubernetes-monitoring   # K8s API monitoring
    resources:
      requests:
        cpu: "200m"
        memory: "6Gi"
      limits:
        memory: "6Gi"           # add a CPU limit (1000m) only if policy requires one

    # Tolerations and node selector for dedicated monitoring nodes (optional)
    tolerations:
      - key: "dedicated"
        operator: "Equal"
        value: "dynatrace"
        effect: "NoSchedule"
    nodeSelector:
      node-type: monitoring
---
apiVersion: dynatrace.com/v1beta6
kind: DynaKube
metadata:
  name: agents
  namespace: dynatrace
spec:
  apiUrl: https://{tenant-id}.live.dynatrace.com/api
  tokens: dynakube
  networkZone: kubernetes
  # add your oneAgent: section here (see ONBRD-05)

  activeGate:
    capabilities:
      - routing                 # route OneAgent traffic
    resources:
      requests:
        cpu: "250m"
        memory: "2Gi"
      limits:
        memory: "2Gi"
    replicas: 3

    # Labels
    labels:
      app.kubernetes.io/component: activegate

Operator 1.11.0+: the sizing guide shows a single DynaKube instead, with platform monitoring under spec.kubernetesMonitoring — ".spec.kubernetesMonitoring is mutually exclusive with the kubernetes-monitoring capability in .spec.activeGate". The dynatrace-api capability is left out here: the DynaKube reference marks it "A custom certificate is required for this capability" (tlsSecretName). spec.networkZone "Sets a network zone for the OneAgent and ActiveGate Pods."

Moving the two-DynaKube layout above to the single form: three things do not carry over on their own.

  • Registration. "With spec.kubernetesMonitoring, cluster registration is not configured automatically. Add registration: {} to keep your cluster registered in Dynatrace."
  • Custom cluster name. A name set with the automatic-kubernetes-api-monitoring-cluster-name feature-flag annotation must be moved "to kubernetesMonitoring.registration.clusterName. Dynatrace Operator does not migrate annotation values automatically."
  • Order. Add spec.kubernetesMonitoring to the routing DynaKube first, and delete the old Kubernetes-monitoring DynaKube only after the KubernetesMonitoringAvailable condition returns True — "Deleting the old DynaKube early causes a monitoring gap."

Sources: DynaKube parameters (DT docs), Size Dynatrace ActiveGates in Kubernetes (DT docs), Consolidate Kubernetes monitoring into a single DynaKube (DT docs) — "The condition returns True when all Kubernetes monitoring resources are ready."

Method 2: Hand-Managed StatefulSet (Documented Container Image)

8. Verifying Deployment

After installation, verify ActiveGate is connected and healthy. ActiveGates surface in Grail as the ACTIVEGATE Smartscape node, so the queries below work directly in a notebook — no REST call needed.

A note on the classic path (ActiveGate 1.343, July 2026): ActiveGate 1.343 deprecates the classic GET /api/v2/activeGates endpoints in favor of this Smartscape node. Separately, ActiveGates have never been reachable through DQL fetch — there is no dt.entity.active_gate entity type in any spelling. Worth knowing precisely how that fails: fetch dt.entity.active_gate does not error — it returns zero rows, which is indistinguishable from "this environment has no ActiveGates." Treat an empty result from a classic entity fetch as a signal to check the entity type exists at all. smartscapeNodes "ACTIVEGATE" is the DQL path. The classic Entities API v2 selector (GET /api/v2/entities?entitySelector=type("ENVIRONMENT_ACTIVE_GATE")) is a different surface from DQL and may still respond during the deprecation period — use it if you need a REST fallback for a tenant that has not yet received 1.343, and migrate the automation on your next maintenance touch.

// ActiveGate inventory - every ActiveGate reporting to this environment,
// with its group, network zone, enabled modules, and host OS.
// Live-verified 07/30/2026. Costs nothing: Smartscape nodes scan 0 bytes of Grail.
smartscapeNodes "ACTIVEGATE"
| fields name, dt.active_gate.id, dt.active_gate.version, dt.active_gate.group.name,
         dt.network_zone.id, is_containerized, os.type, os.version, modules
| sort name asc

// ActiveGate version spread - find the laggards before an update window.
// More than one row means the fleet is not uniform; sort ascending puts the
// oldest version first. Cross-check the OS end-of-support table in section 3
// against the os.version values from the inventory query above.
// ids is listed because names can repeat: two ActiveGate pods in different
// clusters can share a pod name (e.g. dynakube-activegate-0).
smartscapeNodes "ACTIVEGATE"
| summarize {activegates = count(), names = collectDistinct(name), ids = collectDistinct(dt.active_gate.id)},
    by:{dt.active_gate.version}
| sort dt.active_gate.version asc

// ActiveGate count per group and network zone - the HA check.
// Any row showing 1 is a single point of failure for that zone; production
// zones should show 2 or more (see High Availability in section 3).
smartscapeNodes "ACTIVEGATE"
| summarize activegates = count(), by:{dt.active_gate.group.name, dt.network_zone.id}
| sort activegates desc
