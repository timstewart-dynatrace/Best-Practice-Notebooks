You Are Here If…

  • You are net-new to Dynatrace (first tenant being provisioned)
  • You may or may not have a prior observability tool to migrate from
  • The end state is a working Dynatrace tenant covering your priority domains, with operational dashboards, alerting, and access controls in place

If instead you already have a Dynatrace tenant and are adding scope or pulling data from another tool, see Doorway 2 — Expanding or Consolidating. If you are migrating an existing Dynatrace deployment between deployment models, see Doorway 3 — Deployment Migration.

Shared Prologue: Tenant and Account

Before any sub-path: get the tenant operational at the account level.

Step Reading Notes
1. License & tenant provisioning NR2DT — notebook 00 (Step 0 prerequisites) Generalizable beyond New Relic — covers tenant decisions, region, SaaS vs Managed, account hierarchy
2. Initial admin access ONBRD — notebook 01 (First Steps) First-user access, navigation orientation
3. Authentication strategy IAM — notebook 02 (SSO Authentication) Decide SSO method before adding more users

Time: 1–3 days, depending on procurement and SSO complexity.

Sub-Path A — Greenfield

You have no prior observability tool. You are building the practice from zero alongside Dynatrace.

Phase Reading Time
1. Foundation Foundation Module → ONBRD + ORGNZ + IAM in parallel 2–3 weeks
2. Security posture APPSEC — notebooks 01–02 (fundamentals, platform overview) 1 week
3. First domain Pick one from Domain Enablement. For most customers this is K8S (if Kubernetes is in scope) or CLOUD (if AWS, Azure, or GCP). 1–2 weeks
3. First app coverage SPANS for distributed tracing on a critical app; add WEBRUM if web-facing 1–2 weeks
4. Light operationalize DASH notebooks 01..03 (fundamentals, hierarchy, executive); WFLOW notebooks 01..03 (fundamentals, triggers, notification basics) 1–2 weeks
5. Iterate Add domains as adoption grows. Reference Domain Enablement Module. Ongoing

Exit criteria: At least one domain producing useful data; one critical app fully traced; basic dashboards and alerts running.

Sidebar — if you have any existing tool: even if it's a small footprint of synthetic monitors or a few dashboards, follow the relevant migration sub-path (B, C, D, or E) instead of greenfield. Even a small inventory benefits from translation patterns rather than parallel rebuild.

Sub-Path E — Multi-Tool / Hybrid

You have multiple source tools (e.g., New Relic for APM, Splunk or Sumo Logic for logs, native cloud for infrastructure metrics), or you have a security observability mandate alongside APM/infrastructure. The migration runs in waves rather than sequentially.

Recommended sequencing:

Wave Focus Reading
1 Foundation Foundation Module — first; everything else depends on it
2 Security observability APPSEC — full series; run in parallel with Wave 3 if security is a mandate
3 APM (highest pain to migrate, shortest dual-run window) Sub-Path B phases 4–7 if from New Relic; otherwise SPANS + OTEL for native instrumentation
4 Infrastructure K8S and/or CLOUD, depending on environment
5 Logs Sub-Path C or Sub-Path D
6 Frontend WEBRUM, MOBL
7 Synthetic, business events, databases SYNTH, BIZEV, DBMON
8 Operationalize Operationalize Module → ALERT, DASH, WFLOW, AUTOM, AIOPS
9 Cost & maturity FINOPS, SLO, Maturity Module

Anti-pattern: trying to migrate all source tools simultaneously. Each wave should reach a working state before the next begins. Two simultaneous tool migrations halve your team's focus and double the risk of either failing.

Sub-Path F — Dynatrace Managed

You are deploying Dynatrace Managed, the self-hosted, on-premises deployment, rather than a SaaS tenant. This path is Dynatrace Classic only. Most of this playbook assumes SaaS: Grail and the features built on it don't exist on Managed, so the Foundation Module and most domain series don't apply as written. The DTM series is the backbone.

Phase Reading Notes
1. Orientation DTM — notebook 00 (series map) What applies to Managed, where to start, how the series is numbered
2. Design the cluster DTM — notebook 01 (cluster design) Node count, availability model, storage layout — decide before installing
3. Configure the cluster DTM — notebook 02 (cluster configuration) Email, Mission Control, sign-in, privileges, backups
4. Environments and access DTM — notebook 03 (environments) Environment boundaries, identity source, permissions
5. ActiveGates, then OneAgents DTM — notebooks 04 and 05 ActiveGates first: OneAgent installers carry their endpoints
6. Operate DTM — notebooks 10–17 and 99 Five-layer health model and the weekly checklist

Exit criteria: the cluster design written down; the design and configuration review in DTM notebook 99 passed; first OneAgents reporting through Environment ActiveGates; the weekly health check running.

Sidebar — planning to move to SaaS later? See Doorway 3 — Deployment Migration, which routes through M2S.

Shared Epilogue: Where to Next

Once your sub-path is complete, you move into ongoing operations. Recommended next reading:

  • Operationalize Module — DASH → WFLOW → AUTOM → AIOPS sequence
  • Maturity Module — continuous improvement framework via ADOPT
  • Domain Enablement Module — to add additional domains as adoption grows
  • Overlap Map — when you encounter the same topic covered in multiple series

If your situation has shifted from "Net New" to "Expanding / Consolidating" — for example, you completed initial onboarding and are now extending scope — continue to Doorway 2 — Expanding or Consolidating.
