1. Audit Log Fundamentals

Dynatrace audit logs capture all security-relevant events in your environment.

What Gets Logged

Category Events
Authentication Sign-ins (event.type == "LOGIN"), including SSO sign-ins — MFA itself happens in your IdP
Authorization Access attempts, permission checks
User Management User creation, modification, deletion
Group Management Group changes, membership updates
Policy Changes Policy creation, modification, deletion
Token Operations Token creation, revocation, usage
Configuration Settings changes, API calls

Audit Log Fields

Field Description Example
timestamp Event time 2026-01-26T14:30:00Z
event.kind Always AUDIT_EVENT for audit records AUDIT_EVENT
event.type Action LOGIN, GET, POST, CREATE, DELETE
event.outcome Result — success / failure, or an HTTP status success, 403
event.provider Component that recorded the event API_GATEWAY, SETTINGS, API_TOKEN
user.id Acting user (a UUID, not an email address) 37e52d7a-…
user.organization Organization of the acting user DYNATRACE
authentication.type / authentication.grant.type How the caller authenticated OAUTH2, TOKEN
resource The API path or object acted on /platform/document/v1/…
origin.address Client IP address 203.0.113.10
request.source Where the request came from BROWSER, DT_SERVERLESS, OTHER

Two audit records, two places. Activity inside this environment — sign-ins, API calls, settings and token changes — is recorded as AUDIT_EVENT records in dt.system.events, which every query in this notebook reads. Account-level IAM changes — groups, memberships, policies, boundaries — are recorded in the account audit log (Account Management > Settings > Audit log), not here.

Not every action is recorded yet. Dynatrace states that audit events from inside platform services are not recorded yet — its examples are an app installed by AppEngine and a document being shared. An evidence report that needs those actions cannot be built from dt.system.events today; say so in the report rather than presenting an empty result as "no activity".

Sources: Audit logs on Grail (DT docs) — "Grail-based audit logging is active by default in all Dynatrace environments."; "Audit events from within platform services, such as an app being installed by AppEngine or a document being shared, aren't recorded yet."; "Audit events are stored as dt.system.events in the dt_system_events bucket, retained for one year"; the page lists ALLOW iam:users:read; for looking up user details from the user ID. Account Management audit logs (DT docs) — "Dynatrace provides audit logs of changes to your account-level identity and access (IAM) management settings".

Retention Requirements

Environment audit events are kept for one year. Whether that is enough depends on the framework and on how your auditors read it. In community practice, teams commonly plan around figures like the ones below — confirm the period that applies to you with your compliance or legal team before sizing an export.

3. Authorization and Access Events

Track permission checks and access attempts to sensitive resources.

Group, policy, boundary and binding changes are account-level, and this environment's audit events are not their change log. "Dynatrace provides audit logs of changes to your account-level identity and access (IAM) management settings" — "Administrators can view these logs in Account Management > Settings > Audit log", where they are kept for up to ten years (also queryable through the Account Audits API). The same page says "The Account Management audit log doesn't yet cover every account-level change. Some IAM configuration and login events aren't recorded." The query below shows IAM API calls made through this environment — useful for spotting automation, not a change log. 4. Configuration Change Tracking

Track changes recorded in this environment. Account-level IAM changes (groups, policies, boundaries, bindings) are in the account audit log — see the note in Section 3.

User accounts are not in these records. Users are created, invited and removed at account level, so an environment AUDIT_EVENT never describes a user lifecycle change; the CREATE / DELETE events below are settings objects, tokens and lookup files. For joiner-and-leaver evidence, use the account audit log, which covers "Group memberships", together with your IdP's provisioning log when users arrive by SCIM (IAM-06).

5. Compliance Reporting Patterns

Standard queries for compliance frameworks.

SOC2 - Access Control Evidence

SOC2 requires evidence of access controls and monitoring.

// SOC2: Users who signed in during the period
// Corrected 09/24/2026: this cell queried `fetch logs | filter matchesPhrase(log.source, "audit")`,
