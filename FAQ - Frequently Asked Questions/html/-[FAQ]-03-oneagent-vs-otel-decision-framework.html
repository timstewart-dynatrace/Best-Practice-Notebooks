FAQ-03: OneAgent and OpenTelemetry — Choosing Per Workload

Series: FAQ — Frequently Asked Questions | Reference: 03 — OneAgent and OpenTelemetry — Choosing Per Workload | Created: May 2026 | Last Updated: 11/13/2026

Overview

The recurring question:

Three related questions show up repeatedly. Teams already running OpenTelemetry ask: Is it worth the effort to convert our existing OTel-instrumented services to Dynatrace OneAgent? And the sharper version: If our OTel implementation is working today, do we need OneAgent at all? And from teams starting fresh with nothing instrumented yet: We have a clean slate — which should we install first, OneAgent or OpenTelemetry?

The framing that answers all three: OpenTelemetry is the open, vendor-neutral foundation for telemetry — common semantic conventions, reusable integrations, instrumentation that travels across environments and tools. OneAgent adds automation and runtime depth on top of that foundation: instrumentation with no code change, a centrally managed lifecycle, topology, and capabilities that need runtime access — Application Security, Live Debugger and automatic RUM injection. Dynatrace documents the two as working together, not as alternatives, so the useful question is never OneAgent or OpenTelemetry but what fits each workload: OTel only, OneAgent only, or both. Each is a supported end state, and mixed estates are normal.

All three come down to a level-of-effort versus capability-gain trade-off, and all three deserve a frank answer. The answer is the same across every runtime Dynatrace supports — Java, Kotlin, Scala, Groovy, .NET, Node.js, Python, Go, PHP, Ruby — though a handful of runtimes have edge cases (covered in §7 and §14).

Short answer (effort-vs-conversion): If an application is already emitting OpenTelemetry data and runs somewhere OneAgent can reach (long-lived hosts and containers, AWS Lambda through the Dynatrace Lambda layer, and the supported Azure Functions plans — §4), keep OTel for application instrumentation — do not convert. OTel-only is a complete path; add OneAgent alongside it, per workload, where its fully managed host, runtime and infrastructure coverage or its runtime-access capabilities pay off. The two are complementary, not competing. A wholesale conversion is usually a deletion exercise, not a re-instrumentation exercise — and even then, the gain is rarely worth the disruption unless a specific Dynatrace capability is needed that OTel cannot provide on its own.

Short answer (is OneAgent required at all): No, not strictly. OTel alone can fully instrument an application and ship to Dynatrace via OTLP — Davis AI works on that data, traces correlate via W3C traceparent, and metrics/logs land in Grail. OTel-only is a complete path: Dynatrace detects services and service topology from OTel spans, and the OpenTelemetry Host Monitoring extension turns Collector host metrics into host and process entities. What OneAgent adds is fully managed collection — runtime internals (heap / GC / threads / event loop), code-level method tracing, and infrastructure topology without operating a Collector — plus capabilities that need runtime access: Application Security, Live Debugger and automatic RUM injection. Whether those matter depends on the workload — see §2 for the side-by-side capability table.

Short answer (greenfield — which one first?): It depends on what you have already decided. If your organization has chosen OpenTelemetry, instrument with OTel — Dynatrace ingests it natively and detects services, endpoints and service topology from it, and nothing in this FAQ argues you off that choice. If you have no preference and the workload runs on a standard OneAgent-supported runtime (Java / .NET / Node.js / Python / PHP / Go) on long-lived hosts or containers, OneAgent is the lowest-effort start: fully managed, zero code change, time-to-first-trace in minutes. Add OTel when you need custom business spans or open-standard telemetry; the two coexist by design (see §8). Some workloads are OTel by necessity whichever you prefer: serverless platforms OneAgent does not reach (GCP Cloud Functions, and Azure Functions plans outside the supported list — §4), Ruby application code (OneAgent does not inject it), and async-fragmenting runtimes like Scala effect systems (otel4s / zio-telemetry are technically required — see §7).

This FAQ frames the trade-offs, the hidden costs, and the workload-specific edge cases — including async-fragmenting runtimes (effect systems, coroutines, async/await without explicit context propagation) where the choice has a clear technical answer rather than a preference.

1. Framing the Question Correctly

Customers usually ask this as OneAgent OR OpenTelemetry — a binary choice. That framing is the first mistake. The two tools answer different questions:

  • OneAgent answers: "What is happening on my hosts, in my application runtime (JVM / CLR / V8 / CPython / Go runtime / Zend / Ruby VM), and in the frameworks I'm running — without me writing any instrumentation code?"
  • OpenTelemetry answers: "How do I emit portable, vendor-neutral, code-level telemetry from my application — including the parts no agent can see automatically?"

Re-framed correctly, the question becomes: "Given we already have OTel, do we still need OneAgent? And if we add OneAgent, do we need to remove OTel?" The answer to the first depends on the workload: OTel-only is a complete path, and OneAgent is worth adding where its fully managed collection or its runtime-access capabilities (Application Security, Live Debugger, automatic RUM injection) pay off for that workload. The answer to the second is almost never.

Dynatrace frames the platform side the same way: OTel data and OneAgent data are analyzed together "regardless of how you mix your instrumentation choices" — OneAgent on some hosts, OTel on others, both on many. A mixed estate is the expected end state, not a transition to be finished.

2. Is OneAgent Required at All?

Short answer: No. OTel-only is a complete, supported path. Add OneAgent where its fully managed collection or runtime-access capabilities are worth it to you.

OpenTelemetry alone can fully instrument an application and ship to Dynatrace via OTLP. Traces correlate via W3C traceparent, metrics and logs land in Grail, and Davis AI operates on that data. For serverless platforms OneAgent does not reach (GCP Cloud Functions, unsupported Azure Functions plans — §4) and async-fragmenting runtimes that lack agent-side context propagation, OTel is the application-instrumentation layer — on those platforms OneAgent cannot run, and on those runtimes its tracing fragments (§7). A multi-backend or open-standards mandate is a different kind of answer: it settles who owns application instrumentation (OTel), not whether OneAgent adds value alongside it on the hosts and containers it reaches.

Decision rule in three lines:

  • Serverless platform OneAgent does not reach (§4), or async-fragmenting runtime without OTel hooks → OTel for application telemetry. OneAgent can't run there, or its tracing fragments — it still adds host and runtime signals wherever it does run. A multi-backend or open-standards mandate puts OTel in charge of application instrumentation and leaves OneAgent free to add depth alongside it.
  • Standard workloads on long-lived hosts/containers, and fully managed collection, Application Security or Live Debugger matter → add OneAgent alongside OTel. The install is a deployment task — no code change — and the two coexist by design (see §8 for the Span Sensor vs OTLP patterns).
  • OTel is your collection strategy, or it is working today → staying OTel-only is a complete, supported choice. The application telemetry is all there; what you forgo is OneAgent's automation and runtime-access capabilities. Revisit workload by workload when one of them is needed.

Honest framing: OneAgent is not required — OTel data is fully usable in Dynatrace on its own. What OneAgent adds comes in two parts. The first is fully managed collection: host, runtime and infrastructure-topology coverage without operating a Collector fleet, receivers and an attribute strategy yourself. In community practice that is often a total-cost-of-ownership decision more than a feature decision. The second is runtime depth: PurePath, Application Security, Live Debugger and automatic RUM injection, which need runtime access and have no OTel equivalent today. If your Collector estate already runs well, the first part shrinks; the second does not.

3. What Each Tool Actually Is

OneAgent is a Dynatrace-installed binary that runs on the host (or as a container sidecar/initcontainer in Kubernetes via the Dynatrace Operator). When the application runtime starts, OneAgent injects itself and auto-instruments a long list of frameworks and runtimes. It produces PurePath traces, host metrics, runtime metrics, log streams, process snapshots, and Smartscape topology — all without code changes. OneAgent's runtime injection covers Java/Kotlin/Scala/Groovy (JVM), .NET (CLR), Node.js (V8), PHP (Zend), Python, and Go (64-bit Go executables on x86 from OneAgent 1.323, and on AArch64 — net/http, SQL drivers, gRPC, Kafka, MongoDB, Redis, Cassandra and AWS SDK clients per the Go section of the technology-support matrix; on Linux the binary must be dynamically linked unless you use Go static monitoring); for Ruby, which it does not inject, OneAgent still captures host/process telemetry around it.

OpenTelemetry (OTel) is a CNCF specification with a per-runtime delivery model. The two main consumption modes vary slightly per runtime:

Runtime OTel auto-instrumentation entry point OTel manual SDK entry point
Java / Kotlin / Scala / Groovy (JVM) -javaagent:opentelemetry-javaagent.jar io.opentelemetry.api (otel4s, zio-telemetry, kotlinx-coroutines wrappers)
.NET OpenTelemetry.Instrumentation.* NuGet packages auto-wired in Program.cs, or the .NET auto-instrumentation injector System.Diagnostics.ActivitySource / OTel SDK

These OTel modes are independent — you can use any combination, or none. "Already instrumented with OTel" usually means a mix: the auto-instrumentation for HTTP/DB plus some manual SDK calls for business logic.

JVM has a third delivery model. The auto-instrumentation column above shows the static -javaagent: flag, but for JVM workloads there are actually three distinct OTel delivery options, with different operational profiles:

Mode How it loads Operational characteristics
1. SDK in code OTel dependencies in pom.xml / build.gradle; explicit Tracer calls in source Tied to the application build; redeploy needed for instrumentation changes; full control over what is captured
2. Static -javaagent JVM startup flag points at opentelemetry-javaagent.jar — auto-instrumentation kicks in before main() Coupled to the JVM start command; if the agent JAR fails to load (bad version, classpath conflict, missing file), the JVM may fail to start, taking the line-of-business application down with it
3. Runtime attach opentelemetry-runtime-attach (OTel Java contrib) — the application calls RuntimeAttach.attachJavaagentToCurrentJvm() at the beginning of its main() method, and the embedded agent attaches to the running JVM For when the JVM arguments cannot be changed. Needs a code dependency and a full JDK (not a JRE); the call must come from main() on the main thread

Choosing between them. The OTel project positions runtime attach as the route for teams that cannot update the JVM arguments, not as a production default; the OTel pages cited here do not rank the three modes. In community practice, the concern with option 2 is that it puts the agent on the JVM's startup path (a bad JAR or classpath conflict can stop the JVM starting), while option 3 trades that for a code dependency and a JDK requirement — weigh both against your own deployment constraints.

OneAgent takes a different route from all three: its Java code module is loaded as a native JVMTI agent at process start, through automatic process injection — no -javaagent flag in your start command, but also no attach to a JVM that is already running. That is why a new code-module version, or a change to OneAgent's connection settings, takes effect only when the monitored process restarts. It is also why OneAgent updates do not require application redeploys: the start command never references the agent, so a new agent version is picked up at the next workload restart without touching it.

The serverless rule is no longer one rule

"OneAgent does not run on serverless" was never accurate for AWS Lambda, and since OneAgent 1.343 it is not accurate for Azure Functions either. It has to be split by platform — and this matters more here than it would in a reference table, because §9's decision tree treats serverless as a first-question gate, and a wrong answer at a gate misroutes a reader for the life of the project.

  • AWS Lambda — OneAgent reaches it through the Dynatrace AWS Lambda layer, which auto-instruments Python, Node.js, Java and .NET functions without code changes (Go: log monitoring, with statically linked Go monitoring added in OneAgent 1.345). What is not supported on Lambda is the OneAgent SDK — the per-runtime SDK READMEs send serverless users to OpenTelemetry for custom spans, and for Python, Node.js and Java the Dynatrace Lambda extension can pick up that OTel instrumentation in-process once OpenTelemetry interoperability is enabled ("OpenTelemetry": { "EnableIntegration": true } in dtconfig.json, per a Dynatrace Classic page last updated 04/2023). That README statement is about the SDK, not the agent, and it is the source of the common misreading that Lambda is OTel-only.
  • GCP Cloud Functions — OTel is the answer.
  • Azure Functions — now depends on the hosting plan and the runtime, not on "is it serverless". OneAgent 1.343 covers Python on the Flex Consumption Plan (Linux), and Java and Node.js on the Consumption, Premium and Dedicated plans for Windows; 1.347 (staged rollout from 09/30/2026) adds Python on the Premium Plan for Linux. OneAgent 1.349 (staged rollout from 11/09/2026) extends .NET to the Windows Premium and Consumption plans and the Linux Premium and Flex Consumption plans, with an updated implementation for the Dedicated plan. That last item changes the mechanism, not the coverage: on the Dedicated plan "OneAgent runs in full-stack mode", and the Classic integration already reached Functions on the App Service (Dedicated) plan through a site extension. For .NET on the Dedicated plan for Windows, the setup guide adds a prerequisite — the Advanced .NET Instrumentation OneAgent feature, environment-wide or scoped to the Functions' process groups. Until 1.349 reaches the Function, the combinations above are the working coverage. The .NET in-process model reaches Dynatrace end of support on 11/30/2026 (last supported OneAgent 1.351). Any other plan tier or runtime remains OTel-only.
  • Breaking change in 1.343 — set DT_WEBSITE_COMPUTE_MODE where Azure does not. From 1.343, OneAgent reads DT_WEBSITE_COMPUTE_MODE as a fallback when Azure's native WEBSITE_COMPUTE_MODE is absent — for example on the Flex Consumption plan or self-deployed Functions — and without it auto-instrumentation may not work. Set it on those Functions before relying on the agent.
  • And still OTel until the agent is actually there. On the covered Azure combinations, OTel remains the working answer until the OneAgent version deployed on the Function reaches 1.343. Tenant version is not agent version — verify the deployed agent rather than inferring support from your tenant's sprint.

The same release also adds OneAgent Azure SDK tracing for Service Bus (Java, Node.js, Python), Event Hub (Java, Node.js) and Cosmos DB (Python); OneAgent 1.347 (staged rollout from 09/30/2026) adds the Cosmos DB client for Node.js, and OneAgent 1.349 (staged rollout from 11/09/2026) adds Event Hub and Service Bus tracing, sending and receiving, for the Azure SDK for .NET. That bears on this decision for a second-order reason: a Function is often thin, and the spans worth having are the messaging and database calls it makes. Where those dependencies were the reason a team reached for OTel, 1.343 changes the calculus even on Function runtimes it does not cover.

5. What "Convert to OneAgent" Really Means

When customers say "convert from OTel to OneAgent", they often imagine a 1:1 re-instrumentation effort comparable to the original OTel rollout. It is not.

For workloads where OneAgent's automatic coverage is sufficient (the common case — REST/gRPC services on Spring, ASP.NET Core, Express, Django, Rails, plain thread pools or default async runtime), "converting" looks like this:

  1. Install OneAgent on the host or via the Dynatrace Operator on Kubernetes. Restart the processes. Done — instrumentation is live.
  2. Optionally remove the OTel auto-instrumentation (the -javaagent:, the .NET injector, the Node --require, the Python opentelemetry-instrument, the explicit Go middleware imports — OneAgent auto-instruments Go net/http, SQL drivers, gRPC, Kafka, MongoDB, Redis, Cassandra and AWS SDK clients, per its Go support matrix). This step is deletion, not authoring.
  3. Decide what to do with custom OTel spans/metrics/logs in code:
    • Easiest path: leave them in place — Dynatrace ingests OTel data via OTLP, and OneAgent's OpenTelemetry Span Sensor (where supported) stitches them into the same trace as OneAgent's auto-instrumented spans. (Caveat: do not enable both Span Sensor and OTLP export simultaneously, or you will get duplicate spans.)
    • Replacement path: rewrite each Tracer / Meter / Logger call against the OneAgent SDK for your runtime — if one with custom tracing exists (Java, .NET, Node.js, C/C++ and Python — and for Python, Dynatrace recommends OneAgent auto-instrumentation over the SDK). The Go and PHP SDKs only expose trace context for log enrichment and Ruby has no supported SDK, so in those runtimes this path is not available; OTel is the way to emit custom application telemetry. And even where the OneAgent SDK exists, it is intentionally narrow (incoming/outgoing remote calls, custom services, web requests, messaging, SQL, custom request attributes — the Python SDK's feature list is the same shape) and does not cover metrics or logs at all — replacing OTel with the OneAgent SDK necessarily loses the metrics/logs surface unless you separately ingest them via Dynatrace metrics ingest APIs.

For workloads where OneAgent's automatic coverage is insufficient (async-fragmenting runtimes, exotic frameworks, message brokers OneAgent doesn't auto-instrument), removing OTel is actively harmful — you would be deleting working instrumentation and replacing it with nothing.

The realization: "Convert to OneAgent" is rarely a re-instrumentation project. It is an agent installation project, possibly followed by deleting OTel auto-instrumentation if you want to simplify the runtime stack. The custom OTel code in the application generally stays exactly where it is.

7. Async Context Propagation Across Runtimes

This is where the "OneAgent or OTel" choice has a clear-cut technical answer in some runtimes — not a preference.

The mechanic: classical agent-based tracing (both OneAgent's auto-instrumentation and OTel's auto-instrumentation in most runtimes) propagates trace context using a runtime thread-local construct. As long as a request stays on a single thread (or the agent has hooked the thread-pool / scheduling primitives the application uses), context flows correctly. Some runtimes break this assumption.

  • A trace begins on a request, then "loses" context after the first asynchronous boundary
  • Spans appear as orphans (no parent) downstream of the boundary

  • The trace waterfall looks plausibly populated but is structurally wrong

8. The Coexistence Pattern (How They Work Together in Dynatrace)

Dynatrace is explicit that the two are designed to coexist. From the Dynatrace OneAgent + OpenTelemetry documentation: "You can implement this service by service, adopting the open standards of OpenTelemetry where openness matters most, while leveraging enhanced OneAgent features available where you need them."

The mechanism — OpenTelemetry Span Sensor: when this code-module setting is enabled (where supported per runtime), OneAgent detects in-process OpenTelemetry API calls and weaves them into the same trace as OneAgent's auto-instrumented spans. Per the Dynatrace docs: "These auto-instrumented spans are woven together with your manual OpenTelemetry spans into a single trace." The result is a unified PurePath-style trace that contains both OneAgent and OTel-emitted spans, correlated through a shared trace ID.

Critical caveat: if you enable the OpenTelemetry Span Sensor and simultaneously export OTLP from the same process, you will get duplicate spans — once from the Span Sensor's in-process pickup, once from the OTLP exporter. Pick one ingestion path per process. The two supported patterns are:

  1. Span Sensor only — OTel API calls in code, no OTLP exporter configured. OneAgent picks them up locally, ships them inside its native channel.
  2. OTLP only — Span Sensor disabled, OTel exporter configured to send to a Dynatrace OTLP endpoint (or to an OTel Collector forwarding to Dynatrace). OneAgent traces and OTel traces correlate via standard W3C traceparent propagation.

Pattern 1 is documented to weave the OTel spans into the OneAgent trace; with Pattern 2, correlation relies on W3C traceparent propagation — verify the resulting trace structure in your environment. Two things to know before choosing Pattern 1: the docs describe the Span Sensor as "for advanced users only", and on Java, enabling it replaces the application's existing tracers — if the application also exports OTel to another backend, that export stops, so use Pattern 2 there. For runtimes without Span Sensor support (Ruby, and Python where your tenant has no Python switch — see below), for platforms OneAgent does not reach (GCP Cloud Functions, unsupported Azure Functions plans), and for any process without OneAgent, Pattern 2 (OTLP) is the only option.

Span Sensor runtime support: the Use OneAgent with OpenTelemetry page lists Java, Go, Node.js, PHP, and .NET — so Go is a Span Sensor runtime, not an OTLP-only one. The Enable the OpenTelemetry Span Sensor configuration page additionally documents an opt-in OpenTelemetry (Python) switch, and OneAgent 1.347 fixes span-link IDs for OpenTelemetry Python spans captured by OneAgent. The two Dynatrace pages disagree on Python: check for the switch under your tenant's OneAgent features before planning a Python service around Pattern 1.

9. Decision Tree by Workload Type

Plain-language flow:

  1. AWS Lambda or GCP Cloud Functions? → Split them. GCP Cloud Functions: OTel only. AWS Lambda: the Dynatrace Lambda layer auto-instruments Python, Node.js, Java and .NET functions; use OTel for custom spans, because the OneAgent SDK — not OneAgent — is unsupported on Lambda (the per-runtime SDK READMEs direct serverless users to OpenTelemetry for that reason). Go on Lambda is log monitoring, with statically linked Go monitoring added in OneAgent 1.345.
  2. Azure Functions? → Ask two more questions, not one. As of OneAgent 1.343 (released 07/28/2026) Azure Functions is no longer a blanket no: Python on the Flex Consumption Plan (Linux) and Java and Node.js on Consumption, Premium and Dedicated plans for Windows are supported, across multiple trigger types — 1.347 (staged rollout from 09/30/2026) adds Python on the Premium Plan for Linux, and 1.349 (staged rollout from 11/09/2026) extends .NET to the Windows Premium and Consumption and Linux Premium and Flex Consumption plans, with an updated implementation for the Dedicated plan. The .NET in-process model reaches Dynatrace end of support on 11/30/2026 (last supported OneAgent 1.351). So the gate is plan and runtime, not "is it serverless."
    • Outside those combinations → OTel, as before.
    • Inside them → OneAgent is an option, once the OneAgent version deployed on the Function actually reaches 1.343 (1.347 for Python on the Premium Plan for Linux, 1.349 for the .NET plans). Tenant version is not agent version; verify the deployed agent. Until it does, OTel remains the working path. Where Azure does not set WEBSITE_COMPUTE_MODE (Flex Consumption, self-deployed Functions), set DT_WEBSITE_COMPUTE_MODE, or auto-instrumentation may not work (§4).
    • Either way, note that 1.343 also adds OneAgent Azure SDK tracing for Service Bus (Java, Node.js, Python), Event Hub (Java, Node.js) and Cosmos DB (Python), and 1.349 (staged rollout from 11/09/2026) adds Event Hub and Service Bus for the Azure SDK for .NET. If the reason you wanted tracing was the Function's dependencies rather than the Function itself, that may be the more consequential half of the release for you.
  3. Async-fragmenting runtime? (effect systems, coroutines without agent hooks, async without explicit context propagation) → OTel via the runtime-aware library — otel4s / zio-telemetry (Scala effect systems), kotlinx.coroutines OTel instrumentation (Kotlin), contextvars (Python asyncio), AsyncLocal (.NET — handled natively), AsyncLocalStorage (Node.js — handled natively), context.Context (Go — handled natively by the OTel Go libraries). Add OneAgent for host/runtime signals if the workload runs on long-lived hosts or containers.
  4. Chosen OTel as your collection strategy (including an open-standard or multi-backend mandate)? → OTel is a complete path on Dynatrace — services, endpoints and service topology are detected from OTel data, and the OpenTelemetry Host Monitoring extension adds host and process entities. Add OneAgent only where its fully managed collection or runtime-access capabilities pay off for a workload.
  5. Runtime is Ruby? → OTel for application spans; OneAgent adds host/process telemetry and Smartscape. 11. Pros and Cons Side-by-Side

OneAgent — pros

  • Zero-code instrumentation for hundreds of frameworks across Java, .NET, Node.js, Python, PHP, plus Go (net/http, SQL drivers, gRPC, Kafka and more)
  • Host, runtime, process, network, and topology coverage out of the box
  • Smartscape dependency map for hosts, processes, containers and services, filled in automatically
  • Runtime-access capabilities OTel telemetry does not provide: Application Security (Runtime Vulnerability Analytics, Runtime Application Protection), Live Debugger, automatic RUM JavaScript injection
  • Frontend-backend linking for HTML-document and resource requests, through the Server-Timing header OneAgent adds (XHR/Fetch requests link from OTel-captured traces too)
  • Centrally managed updates — no application redeploy
  • Operations-team-friendly (instrument an environment without engineering involvement)

OneAgent — cons

  • Does not run on GCP Cloud Functions or unsupported Azure Functions plans; on AWS Lambda it runs as the Dynatrace Lambda layer, but the OneAgent SDK does not
  • Does not inject Ruby application code (still adds host/process value); Go coverage is limited to the libraries in its Go support matrix, and statically linked Linux binaries need Go static monitoring
  • Default thread-local-style context model fragments under some async runtimes (effect systems, certain coroutine layouts)
  • Custom-span surface (OneAgent SDK) is intentionally narrow — no metrics or log signals; no custom-tracing SDK for Go, PHP or Ruby
  • Framework support is broad but not exhaustive (e.g., http4s, Tapir, niche message brokers, exotic RPC layers)

OpenTelemetry — pros

  • Open standard and vendor-neutral — one instrumentation model and common semantic conventions, exportable to any OTLP-compatible backend, Dynatrace included
  • Full signal coverage — traces, metrics, logs, baggage
  • Per-runtime context-aware libraries (otel4s, zio-telemetry, kotlinx-coroutines, contextvars, context.Context, AsyncLocal, AsyncLocalStorage) handle each runtime's async model correctly
  • Services, endpoints and service topology detected from OTel spans in Dynatrace
  • First-class on serverless across every major runtime
  • First-class on Ruby, where OneAgent doesn't inject application code, and on Go libraries outside OneAgent's Go support matrix
  • Strong community ecosystem, monthly releases, broad plugin coverage
  • Code-level control of sampling, attributes, and span structure

OpenTelemetry — cons

  • Host and runtime coverage means operating Collectors and receivers; host and process entities need the OpenTelemetry Host Monitoring extension
  • No equivalent to on-demand PurePath method tracing
  • Requires application redeploy for SDK changes
  • Analysis quality depends on consistent semantic-convention attributes, which the instrumenting team owns
  • More moving parts (auto-instrumentation, SDK code, Collector) than a single OneAgent install
  • Coverage breadth varies per runtime — JVM and .NET have the deepest OTel coverage; Ruby and PHP are still maturing

12. Is the Conversion Worth the Effort?

Question every customer should ask before starting: "What capability am I gaining that I do not already have, and is it worth the engineering disruption to get it?"

Run through this checklist honestly:

  1. Does my OTel data already land in Dynatrace via OTLP? If yes, you already have most of what "converting" would give you for traces.
  2. Am I missing host, runtime, or infrastructure-topology signals? If yes, either add OneAgent or extend the Collector (hostmetrics plus the OpenTelemetry Host Monitoring extension) — removing OTel solves nothing.
  3. Am I on an async-fragmenting runtime? (Scala effect systems, certain coroutine layouts.) If yes, removing the runtime-aware OTel layer will break tracing — there is no OneAgent equivalent.
  4. Am I on Go, PHP or Ruby? If yes, there is no OneAgent SDK for custom tracing to replace OTel with. Conversion is not technically possible at the application-span level (OneAgent does auto-instrument the Go libraries in its support matrix, so Go keeps that layer either way). On Python an SDK exists, but Dynatrace recommends OneAgent auto-instrumentation over it.
  5. Do I have serverless workloads OneAgent does not reach? GCP Cloud Functions and unsupported Azure Functions plans need OTel, and on AWS Lambda custom spans need OTel because the OneAgent SDK is unsupported there — so a hybrid is unavoidable.
  6. Is there an organizational mandate for open-standard instrumentation or multi-backend export? If yes, OTel owns application instrumentation — and OneAgent can still run alongside it.
  7. What is the cost of a coordinated multi-service rewrite of custom spans, metrics, and logs? Compare honestly against the cost of running both for the foreseeable future.
  8. Is anyone on the team going to maintain a parallel internal instrumentation library against the OneAgent SDK? If not, even partial Path C is a slow walk into instrumentation rot.

Common false economies:

  • "Removing OTel will reduce overhead." In community practice, OTel auto-instrumentation overhead is small enough that removing it after installing OneAgent does not measurably move the needle. OneAgent has its own overhead in the same general range. Exact percentages depend heavily on workload, sampling rate, and exporter configuration — measure in your environment rather than relying on a published number.
  • "One instrumentation model is simpler." True at the code level, false at the platform level — Dynatrace was designed to merge both, and customers running both report fewer surprises than customers running one tool stretched beyond its design center.
  • "OneAgent traces are better than OTel traces." For overlapping framework coverage on standard stacks, the data is comparable. OneAgent's advantage is in what surrounds the spans — host, runtime and topology context, plus runtime-access capabilities such as Application Security and Live Debugger.

The honest answer for almost every team already on OTel: the level of effort to add OneAgent is small (a deployment-engineering task, not a re-instrumentation task). The level of effort to replace OTel with OneAgent is large — and impossible in some runtimes — and almost never repaid by the marginal capability gained. Layer, don't convert.

13. Recommended Approach

Default recommendation for any backend already instrumented with OpenTelemetry:

  1. Keep your OpenTelemetry instrumentation in place. Do not start a conversion project.
  2. Decide per workload whether OneAgent adds enough. Where OTel is your strategy, OTel-only is complete — run the Collector with hostmetrics and activate the OpenTelemetry Host Monitoring extension for host and process entities. Where you want fully managed collection or runtime-access capabilities, install OneAgent on the hosts (or via the Dynatrace Operator on Kubernetes) where the services run, and restart the processes. (For Ruby workloads, OneAgent still adds host/process/Smartscape value even though it doesn't inject application code. For Go, it also auto-instruments net/http, SQL drivers, gRPC, Kafka, MongoDB, Redis, Cassandra and AWS SDK clients per its Go support matrix; on Linux, statically linked binaries need Go static monitoring.)
  3. Pick one of the two supported coexistence patterns to avoid duplicate spans:
    • Pattern 1 — Span Sensor: enable the OpenTelemetry Span Sensor in the OneAgent code module for your runtime; disable any OTLP exporter in the application. OneAgent picks up the OTel API calls in-process. (Available where the OneAgent code module supports it — check per-runtime docs. The docs describe it as for advanced users only, and on Java enabling it replaces the application's existing tracers — if the app also exports OTel to another backend, use Pattern 2.)
    • Pattern 2 — OTLP: keep the OTel exporter pointed at Dynatrace's OTLP endpoint (or an OTel Collector forwarding to Dynatrace); disable the Span Sensor. Spans correlate via W3C traceparent. This is the only option for Ruby (no Span Sensor), for Python where your tenant has no Python Span Sensor switch (§8), for GCP Cloud Functions, and for any process without OneAgent.
  4. For async-fragmenting runtimes (Scala effect systems, certain coroutine layouts), ensure the OTel layer is the runtime-aware library (otel4s, zio-telemetry, kotlinx-coroutines instrumentation) rather than the raw default SDK. Do not attempt to replace this layer with the OneAgent SDK — even where the SDK exists, it has no equivalent of the runtime's async-context primitive.
  5. For serverless workloads, split by platform: AWS Lambda — the Dynatrace Lambda layer plus OTel for custom spans; supported Azure Functions plans — OneAgent once the deployed agent reaches the version that covers the plan and runtime (1.343; 1.349 for .NET, staged rollout from 11/09/2026); GCP Cloud Functions and anything else — OTel only.
  6. Do not rewrite custom OTel spans, metrics, or logs against the OneAgent SDK unless you have a specific Dynatrace capability that the SDK uniquely enables (in practice, this is rarely the case — and there is no custom-tracing SDK for Go, PHP or Ruby, while for Python Dynatrace recommends OneAgent auto-instrumentation over its SDK).
  7. Revisit per workload — as OneAgent coverage grows in your runtimes (new async-aware tracing, new frameworks), more of the stack can move to automatic instrumentation while OTel keeps owning custom spans. Today, layering is the right answer wherever OneAgent runs and its depth is wanted.

14. Deploying to Windows Servers

Short answer: the framework applies to Windows Server unchanged. The OneAgent-and-OTel decision is driven by runtime (Java / .NET / Node / Python / Go / PHP / Ruby) and deployment model (long-lived host vs serverless vs async-fragmenting), not by the operating system. A Java service gets the same answer on Windows as on Linux. What changes on Windows is the weighting of a few factors and the deployment mechanics — covered below.

OneAgent is a first-class citizen on Windows Server

OneAgent installs from an MSI package and runs as a Windows SYSTEM service — the install creates the registry entries that start it at boot. Server Core installations are supported on Long-Term Servicing Channel releases when OneAgent is installed in headless mode (or monitored in an app-only scenario). It delivers the same full-stack deep monitoring it does on Linux: host metrics, process detection, runtime metrics, log streams, Smartscape topology, and PurePath — none of which require a code change. For the current supported Windows Server version list (and the Server Core / LTSC footnote), check the Technology support page linked in the Sources block rather than hard-coding a version here — the matrix moves with each release train.

The decisive Windows factor — .NET Framework and IIS

This is the one place where "which OS" materially changes the recommendation, because the classic, Windows-only .NET Framework stack lives here.

  • OneAgent auto-instruments classic .NET Framework (4.6.2–4.8 and 3.5 SP1; 4.5–4.6.1 reached Dynatrace end of support on 07/31/2026) and modern .NET (.NET 5–10 and .NET Core 3.1; .NET Core 2.1–3.0 reached end of support on the same date), including ASP.NET Framework, ASP.NET Core, WCF, .NET Remoting, gRPC, and the MSMQ client. IIS application pools have built-in instrumentation rules — OneAgent injects into the w3wp.exe worker processes automatically.
  • OTel's .NET auto-instrumentation is strongest for ASP.NET Core and is narrower, more manual, and version-sensitive for classic ASP.NET Framework. On IIS it requires per-application-pool environment-variable wiring.

The practical consequence: on an estate that is predominantly legacy .NET Framework + IIS, OneAgent is the decisive low-effort path to deep coverage — it instruments the classic stack that OTel covers least well, with no code change and no per-app-pool wiring. OpenTelemetry remains the right layer for custom business spans and for open-standard instrumentation; layer it alongside OneAgent (per §8), do not rip it out. For modern ASP.NET Core workloads the coverage gap closes and the choice reverts to the general framework in §9.

Three 1.343 additions that close .NET gaps this section leans on

The argument above — that OneAgent is the low-effort path on a .NET Framework / IIS estate — depends on how completely OneAgent covers the .NET publishing and hosting shapes actually in use. OneAgent 1.343 (released 07/28/2026) closes three of them. As always, verify the agent version on the hosts concerned; a fleet on 1.342 or earlier does not have these yet.

  • .NET single-file self-contained apps are now monitored. This is the load-bearing one. Single-file self-contained publish (PublishSingleFile with a bundled runtime) was a known instrumentation gap, which mattered precisely because it is a common way to ship a self-hosted .NET service onto a Windows box without installing a runtime. A team that had hit that gap would reasonably have concluded OneAgent did not cover their deployment style and reached for OTel — the decision logic in this section would have sent them the wrong way. From 1.343 it is covered.
  • gRPC status codes for .NET are now captured, so a failing gRPC call carries the status rather than surfacing as an opaque error. Relevant to the WCF-replacement pattern, where gRPC is the usual modern successor on Windows service stacks.
  • Kong Gateway Enterprise 3.10–3.14 is supported by the OneAgent NGINX module from OneAgent 1.343, with runtime instrumentation enabled (DT_NGINX_FORCE_RUNTIME_INSTRUMENTATION=1 when starting Kong), which matters where a Windows-hosted .NET estate sits behind Kong rather than IIS ARR or a hardware load balancer.

None of this changes the section's conclusion — it strengthens it, by removing the exceptions that used to argue against it.

Logs and traces on Windows

Both tools deliver logs and traces on Windows — the difference is configuration effort and correlation fidelity.

Logs

  • OneAgent auto-detects and ingests the Windows Event Log channels (System / Application / Security) and text log files (IIS logs, custom application logs). It is enabled by the [Built-in] Windows system, application, and security logs log-ingest rule, or included automatically under [Built-in] Ingest all logs. Each log line is auto-correlated to the host / process / service entity that produced it.
  • OpenTelemetry-only reads the Event Log via the Collector's windowseventlogreceiver (the channel: field is required — e.g. Application, System, Security) and text logs via the filelog receiver, then exports OTLP. You configure each channel and path and own the attribute hygiene that ties logs back to entities.

Traces

  • OneAgent PurePath auto-captures traces for .NET (including IIS w3wp.exe), Java, and Node on Windows with no code change. Critically, it traces the classic Windows service stack — ASP.NET Framework, WCF, .NET Remoting, gRPC, and the MSMQ client — which OTel's .NET auto-instrumentation covers least well.
  • OpenTelemetry-only spans come from the .NET auto-instrumentation injector / SDK and export via OTLP; they correlate with OneAgent spans through W3C traceparent (per §8). Coverage of classic .NET Framework / WCF / MSMQ is narrower, so some Windows service hops can be missing unless manually instrumented.
